# Целевой объём

| Величина | Значение |
|---|---|
| Задач в работе | ~380 (300 train + 40 held-out A + 40 held-out B) |
| Кадров собрать | ~1500 — запас на отбраковку |
| Городов | 30–40, распределённых по континентам |
| Кадров на город | ~50 |

Объём в единицы гигабайт, выгрузка укладывается в вечер.

# Шаги

1. **Список городов.** Составить заранее, с явными квотами и разметкой на страты: часть стран резервируется исключительно под held-out B и в train-поток не попадает ни одним кадром.
2. **bbox-запросы.** Вокруг каждого города несколько плиток в пределах [ограничения 0.01 кв. градуса](/data/mapillary.md).
3. **Фильтрация.** Отбраковка по `quality_score`; фильтр по `captured_at`, чтобы не смешивать съёмку разных эпох в пределах одной страты.
4. **Загрузка кадров** в разрешении `thumb_1024` или `thumb_2048`.
5. **Сохранение метаданных** — вместе с кадром пишутся: `computed_geometry`, страна, `captured_at`, `quality_score`, **автор и ссылка для атрибуции**, стабильный `task_id`.
6. **Заморозка.** Снапшот фиксируется и далее не меняется. API во время прогонов не вызывается вообще.

# Почему заморозка обязательна

Требование [детерминизма](/evaluation/measurement-protocol.md): один и тот же чекпоинт памяти на одном и том же held-out обязан давать один и тот же результат. Живой API даёт меняющуюся выдачу, зависимость от сети и риск падения демо на сцене.

# Порядок работ

Выгрузку стоит начинать раньше остального: она ни от чего не зависит, а без неё невозможна калибровка baseline, от которой зависит имеет ли смысл писать движок опыта.
