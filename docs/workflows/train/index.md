# Система обучения Loci

## Назначение

Обучение Loci состоит не из одного линейного workflow, а из нескольких циклов с разной частотой,
входами и критериями завершения. Такое разделение не позволяет смешивать:

- честное решение одной фотографии;
- гипотезу, полученную из единичного эпизода;
- знание, проверенное на независимых примерах;
- транспортную доставку данных;
- доказанное улучшение качества агента.

В рамках этих процессов обучение означает адаптацию через внешнюю память. Весы базовой модели не
изменяются.

Слепую геолокацию внутри train-попыток и benchmark выполняет общий
[решатель](../locate.md), используемый также production-инференсом.

## Циклы

| Цикл | Частота | Основной результат |
|---|---|---|
| [Отбор примеров](select.md) | Перед следующей обучающей партией | Дедуплицированный и сбалансированный `training_batch` |
| [Обработка попытки](attempt.md) | Для каждого train-примера | `episode`, `memory_feedback[]`, `learning_candidate[]` |
| [Валидация знаний](validate.md) | После появления новых кандидатов или по расписанию | `validated learning_observation[]`, кандидат версии памяти |
| [Оценка памяти](evaluate.md) | Перед публикацией версии и периодически | `evaluation_report`, решение `publish | reject | rollback` |

Между попыткой и валидатором действует отдельный [контракт событий](events.md): archive episode
остаётся source of truth, а очередь доставляет идемпотентный указатель на принятую версию.

## Как циклы соединяются

```text
┌──────────────────────────────────────────────────────────────┐
│ Отбор примеров                                               │
│    баланс + пробелы + ошибки + запросы на контрпримеры       │
└───────────────────────────────┬──────────────────────────────┘
                                ↓
┌──────────────────────────────────────────────────────────────┐
│ Обработка попыток                                            │
│    blind answer → reveal → review → archived episode + event │
└───────────────────────────────┬──────────────────────────────┘
                                ↓
┌──────────────────────────────────────────────────────────────┐
│ Валидация знаний                                             │
│    grouping → evidence → counterexamples → validated records │
└───────────────────────────────┬──────────────────────────────┘
                                ↓
┌──────────────────────────────────────────────────────────────┐
│ Оценка версии памяти                                         │
│    frozen benchmark → memory off/on → regression gate        │
└───────────────────┬───────────────────────────────┬──────────┘
                    │ publish                       │ reject
                    ↓                               ↓
             рабочая память              причины регрессии
                    │                               │
                    └───────────────┬───────────────┘
                                    ↓
                         следующий цикл отбора
```

## Общие сущности

### Попытка

Один слепой ответ на одну фотографию с последующим reveal. Попытка завершается после долговечной
фиксации эпизода и исходящих операций.

```text
attempt_id
image_ref
run_context
answer_snapshot
ground_truth
evaluation
post_analysis
```

### Учебный кандидат

Атомарная гипотеза из одного train-эпизода. Она хранит наблюдение, предусловия, направление
влияния, географическую цель и конкурирующие варианты. Кандидат не индексируется как активное
знание.

```text
learning_candidate
  validation_status — proposed | quarantined
```

### Валидированное наблюдение

Результат сопоставления нескольких независимых train-групп, включая контрпримеры. Только такая
запись может быть предложена рабочей памяти.

```text
learning_observation
  epistemic_status — validated_association
  source_attempt_ids[]
  support
  applicability
  known_exceptions[]
```

### Версия памяти

Неизменяемый снимок активных знаний и индекса, который можно воспроизвести в benchmark:

```text
memory_snapshot
  snapshot_id
  parent_snapshot_id | null
  knowledge_versions[]
  index_version
  created_at
  publication_status — candidate | active | rejected | rolled_back
```

### Контрольный отчёт

Сравнение одной или нескольких версий памяти на неизменяемом наборе примеров при фиксированной
конфигурации агента.

```text
evaluation_report
  benchmark_version
  stage_outcomes
  budget_usage
  run_matrix
  geolocation_metrics
  response_policy_metrics
  hint_metrics
  calibration_metrics
  memory_metrics
  cost_metrics
  decision
```

### Production-конфигурация

Публикация атомарно связывает проверенные версии решателя, памяти и калибровки:

```text
production_configuration
  configuration_id
  agent_version
  model_id
  prompt_version
  primary
    memory_mode — snapshot
    memory_snapshot_id
    calibration_policy_id
    execution_mode — normal
  fallback
    memory_mode — off
    calibration_policy_id | null
    execution_mode — production_fallback
  tool_contract_versions
  geocoder_provider
  geocoder_version
  response_policy_id
  publication_report_id
```

Publication step регистрирует primary и fallback как одну атомарную конфигурацию.
Production-инференс закрепляет её целиком до начала solve, а rollback переключает всю пару.

## Разделение данных

```text
train
  используется для попыток, учебных кандидатов и подтверждения знаний

validation
  используется для настройки политик и порогов
  не подтверждает конкретные знания и не пишет в рабочую память

test
  используется только для итогового regression gate
  не выполняет учебный review и не изменяет знания, выборку или политики
```

Split назначается до запуска агента на уровне групп:

- near-duplicate изображений;
- одной точки или объекта;
- сессии и кампании съёмки;
- других источников сильной корреляции.

Эпизоды validation/test могут храниться в аналитическом архиве, но не используются валидатором
как поддержка или контрпример конкретного знания.

## Разные значения слова «успех»

```text
attempt recorded
  эпизод и outbox долговечно сохранены

delivery accepted
  внешнее хранилище приняло payload

knowledge validated
  гипотеза прошла заданную политику проверки

memory snapshot built
  валидированные записи собраны в воспроизводимую версию

learning demonstrated
  версия прошла парный benchmark и regression gate
```

Ни одно предыдущее состояние не подразумевает автоматически следующее.

## Сквозные инварианты

- Ground truth скрыт до фиксации слепого ответа.
- Split и группы назначены до просмотра результата.
- Один эпизод создаёт гипотезу, а не универсальное правило.
- Только train-эпизоды участвуют в валидации знаний.
- Test не влияет на память, политики и выбор следующей партии.
- Все модели, промпты, инструменты, данные и версии памяти воспроизводимы.
- Физические признаки отделены от артефактов источника съёмки.
- Временные и доменные ограничения знания сохраняются явно.
- Архив эпизодов отделён от памяти пользовательского инференса.
- Подтверждение доставки не считается доказательством обучения.
- Публикация пары memory snapshot и calibration policy обратима через предыдущую production-конфигурацию.

## Наблюдаемость системы

Для каждого перехода между циклами сохраняются:

```text
event_id
entity_id
source_cycle
target_cycle
schema_version
content_hash
created_at
delivery_status
```

Для перехода attempt → validation используется `validation_event` с archive receipt и content
hash; полный feedback и candidates повторно в очередь не копируются.

Это позволяет ответить:

- из каких попыток возникло знание;
- какие контрпримеры изменили его область применимости;
- в какую версию памяти оно вошло;
- на каком benchmark эта версия была принята;
- какая ошибка или пробел инициировали следующий набор примеров.

## Контракты инструментов

Циклы используют существующие инструменты следующим образом:

| Инструмент | Цикл |
|---|---|
| [`memory_retrieve`](/tools/memory_retrieve.md) | Общий blind solver в production, train и benchmark |
| [`geocode_search`](/tools/geocode_search.md) | Разрешение уже сформированных топонимов в общем solver |
| [`geocode_reverse`](/tools/geocode_reverse.md) | Нормализация выбранных координат в solver и ground truth после reveal |
| [`episode_store`](/tools/episode_store.md) | Архивирование завершённой попытки |
| [`memory_store`](/tools/memory_store.md) | Публикация только валидированных наблюдений |

Контракты памяти поддерживают:

- фиксированный `memory_snapshot_id` для воспроизводимого retrieval;
- происхождение, validation status, область применимости и срок актуальности записи;
- агрегированные знания с несколькими `source_attempt_ids`;
- стабильный `knowledge_id`, версии и `supersedes`;
- requested/served snapshot IDs и явный `snapshot_mismatch`.

Feedback по ранее извлечённым ссылкам поступает валидатору через archive episode и
`validation_event`, а не через agent tool.

## Результат полного контура

Один проход системы обучения считается завершённым, когда:

1. обработана выбранная партия train-примеров;
2. episodes архивированы, а validation events обработаны либо имеют явный terminal status;
3. новые кандидаты прошли валидацию либо остались в карантине с явной причиной;
4. сформирован кандидат версии памяти;
5. версия прошла staged benchmark и calibration sample policy;
6. принято и записано решение `publish`, `reject` или `rollback` для primary/fallback bundle;
7. ошибки и пробелы переданы следующему циклу отбора.

Только решение `publish`, основанное на контрольном отчёте, позволяет утверждать, что накопленный
опыт улучшил текущую конфигурацию Loci.

## За пределами раздела

- изменение весов базовой мультимодальной модели;
- обучение визуального encoder или detector;
- внутренняя реализация индекса и консолидации памяти;
- работа с несколькими фотографиями одного места;
- активный запрос дополнительных изображений;
- произвольный внешний поиск помимо определённых инструментов.
