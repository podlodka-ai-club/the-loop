# Tools памяти и по-признаковый `observe`/`reflection`

## Цель

Понять, как перевести текущий benchmark-агент от подстановки общего списка hints к процессу,
в котором агент извлекает признаки фотографии, отдельно обращается к памяти по каждому признаку,
использует сгруппированные воспоминания для ответа, а после reveal создаёт отдельный урок для каждой
пары «признак + ответ памяти». Исследование нужно до ADR и spec, потому что изменение затрагивает одновременно
модель вызова LLM, контракт памяти, стоимость запуска и воспроизводимость оценки.

## Статус утверждений

В документе смешаны три типа материала:

- **Текущее состояние** — наблюдение по файлам в `src/` и существующим TypeScript-контрактам.
- **Ограничение** — свойство benchmark или правило безопасности, которое нельзя потерять при
  изменении flow.
- **Гипотеза** — кандидатное направление, которое нужно подтвердить в ADR/spec и тестах.

Утверждения о function calling относятся к официальному API-контракту; совместимость конкретного
OpenRouter-маршрута и используемой модели с нужными tool-вызовами ещё нужно проверить отдельно.

## Короткий вывод

Основная проблема — не отсутствие tools само по себе, а глобальное ранжирование, в котором редкие
специальные признаки конкурируют с широкими и проигрывают им. Наиболее подходящим направлением
выглядит feature-scoped retrieval, реализованный через гибридный tool-loop:

- модель сама формирует вызовы `memory_retrieve` и получает результаты как данные, но отдельный
  вызов относится только к одному feature;
- приложение разделяет фазы `observe`, `retrieve`, `analyze` и `reflect`, ограничивает число вызовов
  и проверяет, что каждый видимый признак был обработан;
- `memory_store` появляется только в отдельной post-reveal фазе рефлексии;
- рефлексия возвращает набор episode-level lessons: один lesson связан с одной парой «feature +
  memory hit», а не со всей фотографией.

Простая смена memory backend или улучшение только транспорта проблему не решает: отдельные группы
нужны для того, чтобы редкий cue не участвовал в одном рейтинге с `road`, `flat` и `horizon`.
Свободный tool-loop лучше соответствует идее «агент умеет пользоваться памятью», но не гарантирует
запрос по каждому признаку. Гибрид сохраняет агентность и даёт приложению контроль над coverage,
но требует явного журнала вызовов и правил завершения.

В рекомендуемом варианте обязательный список видимых `feature.key` строит приложение. Для каждого
ключа оно разрешает один активный `memory_retrieve`; модель формирует query и получает ответ через
tool-loop. Если модель пропустила ключ, повторила его или вернула неверные аргументы, приложение
не считает ключ покрытым: оно либо делает ограниченный retry, либо фиксирует `skipped` и продолжает
с неполной памятью. Таким образом, tools остаются реальными вызовами агента, но coverage не зависит
только от его решения.

## Что есть сейчас

Текущая реализация уже разделена на точки, которые можно развивать, но её семантика пока другая:

- [`src/agent.ts`](/src/agent.ts) делает один `chat.completions.create` и получает структурированный
  `Guess`. Память приходит в prompt как готовый текст; tools модели не передаются.
- [`src/task.ts`](/src/task.ts) сначала вызывает один `memory.recall(features, limit)`, затем solver,
  а `learn` запускает только после успешного ответа solver.
- [`src/observe.ts`](/src/observe.ts) может сделать отдельный vision-вызов и возвращает общий массив
  из 12 фиксированных слотов. Это поисковый запрос, а не полноценная модель признаков.
- [`src/reflect.ts`](/src/reflect.ts) повторно отправляет изображение, guess и ground truth и
  возвращает один `LessonInput` с `content`, `triggers` и `region`.
- [`src/memory/memory.ts`](/src/memory/memory.ts) принимает массив features одним recall-вызовом и
  сохраняет один lesson за раз. В типах нет идентификатора признака и нет связи «этот результат
  памяти относится к этому признаку».
- [`src/memory/file/memory.ts`](/src/memory/file/memory.ts) в режиме `all` отдаёт весь store и
  игнорирует limit; в режиме `top` делает простое пересечение слов triggers с query. Поэтому
  переход к отдельному поиску по признакам потребует пересмотреть режим `all`: иначе один и тот же
  полный store будет возвращаться для каждого признака.
- [`src/memory/select.ts`](/src/memory/select.ts) сейчас подключает в основном runtime только
  `file` и `mem0`; адаптеры Hindsight и xmemory существуют отдельно и не участвуют в выборе
  backend для `experiment.ts`.

Это означает, что задача не сводится к добавлению двух функций. Нужно сохранить provenance:
какой признак породил запрос, какие memories вернулись и какой lesson был из них сформирован.

## Что показал PR #10

Отчёт [PR #10](https://github.com/podlodka-ai-club/the-loop/pull/10) проверил гипотезу о проблеме
извлечения признаков и retrieval на одних и тех же 100 кадрах. Доставка памяти была рабочей, но
глобальный отбор не показал устойчивого улучшения:

| Режим | geoscore | Медиана ошибки | `<200 км` |
|---|---:|---:|---:|
| baseline, без памяти | 2479.4 | 830.6 км | 11 |
| file, all-28 | 2527.9 | 804.8 км | 9 |
| file, top-5 | 2187.7 | 928.2 км | 6 |
| Mem0, top-5 | 2239.0 | 934.1 км | 6 |

В `top`-режиме широкие triggers набирали больше пересечений: `flat horizon` и `paved road`
подходили почти к каждому кадру, а специфичные признаки почти не попадали в top-K. Поэтому
векторный поиск Mem0 и токеновое пересечение FileMemory дали практически неразличимый результат.

Есть и граница, которую ranking не исправит: на 49 из 99 кадров страна была названа правильно,
но медиана ошибки внутри правильной страны составляла 515.8 км. Все 28 проверенных lessons были
правилами выбора страны, а не локальными признаками для выбора точки. Значит, feature-scoped
retrieval решает потерю особых cues, но не создаёт отсутствующее в памяти знание.

## Термины и единица работы

| Термин | Смысл в этом исследовании |
|---|---|
| `attempt` | Обработка одной фотографии: blind solve, reveal и связанные с ними memory calls |
| `feature` | Наблюдаемый слот из observe; это не memory и не гипотеза о стране |
| `memory hit` | Один результат чтения от memory provider по конкретному feature |
| `episode` | Одна пара `attempt + feature + memory hit`, которую reflection разбирает отдельно |
| `payload` | Provider-native данные, обёрнутые результатом tool |
| `lesson` | Новый переносимый опыт по одному episode, созданный reflection и предназначенный для записи |
| `coverage` | Для feature зафиксирован retrieval result, ошибка или явный пропуск |

Предварительная рабочая модель — один attempt на всю фотографию, один observe-результат, один
логический retrieval на feature и отдельный episode для каждого возвращённого memory hit. Если
feature вернул несколько hits, reflection запускается по каждому из них, не смешивая их в один
lesson. Это не означает один HTTP-вызов: tool-loop может потребовать несколько model round-trips,
а отдельный provider-call может быть асинхронным.
Следующая стадия должна отдельно зафиксировать, передаётся ли изображение в каждом model round-trip
или только в первом контексте, и где именно заканчивается каждая фаза.

## Как понимать новый flow

### Observe

`observe` должен возвращать не просто строки, а стабильные записи признаков. У каждой записи нужны
как минимум:

```text
feature
  key       # стабильный слот, например traffic_side или vegetation
  text      # только то, что видно на изображении
  visible   # true/false; not visible не становится запросом к памяти
```

Текущие 12 слотов можно рассматривать как гипотезу для начального vocabulary: они дают
повторяемость и заставляют модель проверять дорожную сторону, текст, столбы, разметку,
растительность и другие зоны. При этом надо отделить `not visible` от реально наблюдаемого
признака. Иначе память будет получать запросы вроде «признак не виден», которые не помогают
геолокации. Boolean `visible` может оказаться слишком грубым: минимум нужно различить
`not_visible`, `visible`, `uncertain` и `uninformative`, либо явно решить, что последние два
состояния обрабатываются как `visible`.

### Retrieve

Для каждого признака, который policy считает eligible, приложение запускает tool-capable диалог. Агент вызывает
`memory_retrieve` с одним коротким запросом, относящимся к одному feature. Результат сохраняется в
журнале с `feature.key`, исходным query, payload или ошибкой. После этого результат группируется
рядом с тем же признаком, например:

```text
vegetation
  observed: dry scrub, sparse grass
  memories: [ ... ]

road_markings
  observed: single yellow centre line
  memories: [ ... ]
```

Важно, что memory payload — подсказка, а не инструкция. Агент должен сверять его с пикселями и не
делать вывод только потому, что воспоминание уверенно сформулировано.

### Analyze

После завершения retrieve отдельный финальный ответ получает изображение, список наблюдений и
сгруппированные результаты памяти. На этой фазе memory tools для чтения уже не нужны: это делает
границу анализа понятной и позволяет записать полный контекст solve. В ответе остаётся текущий
`Guess`, а в telemetry добавляется карта `feature -> memory calls`.

### Reflection

После reveal reflection не объединяет все memory hits одного feature и не пишет один общий lesson
на фотографию. Каждый `feature + memory hit` становится отдельным episode. Для него reflection
получает:

- изображение и точное описание видимого признака;
- один конкретный memory hit, который был извлечён именно по этому признаку;
- зафиксированный blind guess и, при необходимости, финальный анализ;
- правильное место и расстояние до него.

Reflection делает явный вывод о роли этой пары: memory hit помог, был нейтрален/нерелевантен,
ввёл в заблуждение или оказался недостаточным. В lesson нужно сохранить не только географический
вывод, но и эту оценку: что сработало, что не помогло и какая ошибка возникла. Даже отрицательный
вывод может быть полезным counter-signal, если он grounded в изображении и ground truth.

Каждый успешный reflection episode даёт отдельный `memory_store` вызов и отдельный lesson с
provenance `attempt`, `feature` и `memory hit`; в lesson сохраняется и отрицательный verdict, если
он grounded. Если memory по feature не вернула ни одного hit, pair-episode не создаётся: фиксируется
no-hit outcome, а отсутствие памяти не маскируется под найденный урок.

`memory_store` не должен быть доступен в blind observe/analyze-контексте: ground truth и право записи
появляются лишь после reveal. Сбой одного episode не должен откатывать lessons других episodes;
частичный результат должен различать `reflected`, `not_useful`, `stored`, `write_failed` и
`write_outcome_unknown`.

## Кандидатные подходы

С точки зрения ranking рассматриваются три направления:

- **Весь store без отбора** сохраняет редкие lessons, но раздувает prompt и не различает полезные
  воспоминания для конкретной фотографии.
- **Улучшенный global score** с IDF/BM25 или нормировкой уменьшает преимущество частых слов, но все
  типы признаков по-прежнему конкурируют в одном top-K.
- **Feature-scoped score** строит отдельный bounded result для каждого признака и передаёт анализу
  группы без повторного global top-K. Это выбранное направление; tools здесь являются каналом
  вызова и provenance, а не самостоятельным решением ranking.

| Подход | Что даёт | Основной риск | Стоимость и контроль |
|---|---|---|---|
| Свободный tool-loop | Модель сама выбирает, какие признаки искать и когда остановиться | Может пропустить признак, повторить запрос или начать писать память не в той фазе | Число вызовов и latency непредсказуемы |
| Полностью управляемый workflow | Приложение само вызывает recall для каждого feature и reflection для каждого lesson | Модель фактически не является tool-using agent; её выбор запроса не проверяется | Максимально детерминированно и дёшево контролировать |
| Гибридный tool-loop | Модель формулирует и вызывает tools, приложение задаёт фазы, лимиты и обязательные feature keys | Нужно обрабатывать неполные/повторные tool calls и вести журнал | Предсказуемо при фиксированном лимите, но дороже текущего flow |

Свободный режим не подходит как единственный production-контракт: официальный tool-calling API
разрешает модели сделать ноль, один или несколько вызовов за ход, а затем приложение должно
исполнить вызовы и передать результаты обратно модели. Это естественно для агента, но само по себе
не означает «по одному вызову на каждый видимый признак». В strict-схемах нужно также сделать
`additionalProperties: false` и объявить все поля required. См. [официальное руководство OpenAI по
function calling](https://developers.openai.com/api/docs/guides/function-calling).

Для Loci разумно использовать tools как реальный канал общения с моделью, но проверять coverage
в приложении: сохранять множество `feature.key`, запрещать повторную обработку уже закрытого ключа,
ограничивать число итераций и завершать retrieve только после покрытия всех видимых признаков или
явной фиксации пропуска.

### Управление обязательными вызовами

Здесь есть два непротиворечивых варианта внутри гибридного подхода:

1. Приложение планирует feature-вызовы и по одному разрешает модели вызвать `memory_retrieve` для
   текущего ключа. Это гарантирует coverage и делает число запросов известным.
2. Модель сама выдаёт batch tool calls, а приложение валидирует множество ключей, выполняет только
   допустимые вызовы и повторно запрашивает недостающие. Это уменьшает число round-trips, но сложнее
   для моделей и провайдеров.

Первый вариант безопаснее как v1 для benchmark. Свобода модели остаётся в формулировке query и в
решении, как использовать memory hit, а не в соблюдении обязательной структуры эксперимента.

## Что изменится в контрактах

### Read tool

Нужен общий function tool вроде `memory_retrieve` с обязательными полями `feature_key` и `query`.
`memory_ref` лучше оставлять в контексте workflow, а не позволять модели выбирать backend. Один
вызов должен быть связан ровно с одним признаком; provider-specific адаптер по-прежнему может
преобразовывать query в нативный поиск.

Текущий `Memory.recall(features: string[], limit)` можно временно вызвать как
`recall([query], limit)`, но один вызов должен быть сделан отдельно для каждого feature. Результаты
нельзя затем снова смешивать в один global top-K, иначе исходная проблема вернётся. Для будущего
контракта нужно решить, возвращает ли tool общий нормализованный массив `Hint[]` или provider-native
payload, и как сохранить scores/metadata без привязки workflow к одному backend.

### Write tool

`memory_store` должен принимать lesson, который относится к одному episode — одному feature и одному
memory hit. Минимально это можно кодировать в content, но надёжнее добавить машинные поля
`feature_key`, `memory_hit_id`, `source_attempt_id`, `effect` и `idempotency_key` рядом с текстом.
Иначе разные lessons на одном фото нельзя будет отличить при повторной записи или оценить по
отдельности.

Запись должна быть разрешена только в post-reveal reflection. Если tools остаются в одном API
клиенте, доступ к `memory_store` всё равно надо ограничивать по фазе; предпочтительнее передавать
только `memory_retrieve` в blind-контекст и только `memory_store` в reflection-контекст.

### Lesson

Один lesson на episode должен содержать наблюдение, конкретный memory hit, связь с правильным местом,
переносимое различение и оценку роли памяти (`helped`, `irrelevant`, `misleading` или
`insufficient`). `triggers` должны описывать наблюдаемые признаки без названия страны, как и сейчас.
Нужна явная политика для:

- признаков `not visible`;
- видимых, но бесполезных признаков;
- нескольких memory hits по одному feature — каждый разбирается отдельным episode;
- урока, который противоречит памяти или не подтверждается изображением.

Рекомендуемая логическая связь выглядит так:

```text
attempt
  └─ feature
       ├─ observed text
       ├─ retrieve calls[]
       └─ memory hit
            ├─ reflection result
            └─ stored lesson | null
```

Она не обязана буквально повторять внутреннюю модель конкретного memory provider, но должна быть
доступна в trace/evaluation, иначе нельзя будет понять, улучшил ли ответ именно нужный урок.

Есть отдельный выбор формата записи:

| Формат | Плюс | Минус |
|---|---|---|
| Только текст с feature внутри | Совместим с текущим `memory_store` и всеми адаптерами | Провайдеру и evaluation трудно надёжно извлечь feature и повтор записи |
| Текст плюс `feature_key`/provenance metadata | Сохраняет связь машинно и упрощает deduplication | Требует расширить общий контракт и проверить все backends |
| Один общий lesson с секциями по features | Меньше write-вызовов | Нарушает требование отдельного урока и ухудшает feature-level retrieval |

Для заявленного поведения третий вариант выглядит слабым. Между первым и вторым нужен отдельный
решающий выбор в ADR; исследование не считает его уже утверждённым.

## Ограничения и риски

1. **Рост стоимости.** Сейчас на фото обычно приходится один solver-вызов и, при необходимости,
   один observe-вызов. Новый flow добавляет до 12 retrieval-вызовов, а обучение — до `12 × top-K`
   reflection и write-операций, если каждый memory hit становится episode. Нужны лимит признаков,
   ограничение top-K и измерение token/latency budget.
2. **Неполное покрытие.** `tool_choice: auto` не гарантирует вызов по каждому feature. Coverage
   должен проверяться приложением, а не только prompt-инструкцией.
3. **Параллельность и провайдеры.** Независимые чтения можно выполнять параллельно, но текущий
   OpenRouter workflow уже сталкивается с rate limit. Для benchmark нужен ограниченный concurrency
   и запись порядка вызовов; hosted memory может дополнительно иметь задержку ingestion/visibility.
4. **Ошибка памяти.** Ошибка по одному признаку не должна уничтожать всю фотографию: нужно вернуть
   пустой результат именно для этого feature и отметить limitation. При этом ошибка tool protocol,
   неверный `memory_ref` и исчерпание общего бюджета могут быть terminal для run.
5. **Prompt injection в memories.** Сохранённый текст и provider-native payload — данные. Их нельзя
   передавать как инструкции и нельзя позволять memory result менять доступные tools, `memory_ref`
   или фазу workflow.
6. **Дубликаты и неизвестный исход записи.** Отдельный lesson на каждый feature увеличивает число
   повторов. Для hosted backends нужен idempotency policy; timeout после принятой записи нельзя
   бездумно повторять. Для локального `FileMemory` текущая генерация id по длине файла не рассчитана
   на безопасные повторы и параллельные writer-ы.
7. **Сравнимость benchmark.** Memory-on и memory-off должны использовать одинаковый список
   наблюдений и одинаковую политику feature keys. Кэш `observe` уже помогает, но изменение числа
   vision/tool-вызовов нужно отражать в метриках и baseline, иначе сравнение будет измерять не только
   влияние памяти.
8. **Изоляция benchmark.** Текущий код уже исключает из train-корпуса eval IDs и соседние sequence,
   а evaluation читает `FrozenMemory` и не пишет в него. Новый flow должен сохранить это правило:
   evaluation запускается только с явным frozen snapshot, никогда не вызывает `memory_store`, а
   memory-on и control используют один и тот же snapshot и порядок попыток. Нужно различать cold run
   с пустой памятью и warm run с заранее указанным snapshot; live store нельзя молча использовать
   как baseline.
9. **Различия адаптеров.** File и Mem0 возвращают список hints, Hindsight и xmemory имеют более
   provider-native семантику. Общий tool должен сохранять различия в payload, но не требовать от
   solver знать внутренний API backend.
10. **Memory poisoning.** Ошибочный или инъекционный lesson может влиять на множество следующих
    попыток. Нужны provenance, версия/снимок, возможность quarantine или rollback и policy доверия
    к урокам, а не только idempotency key. Сам факт, что lesson сгенерирован моделью, не делает его
    истинным.

## Предлагаемая граница первой реализации

Для следующей стадии достаточно зафиксировать узкий vertical slice:

- оставить текущие 12 observe slots и добавить стабильный `feature_key`;
- запрашивать память только по видимым slots;
- использовать один нормализованный `memory_retrieve` с одним feature за вызов;
- передавать memory result в analyze, сгруппировав его по `feature_key`;
- после reveal запускать reflection отдельно на каждый `feature + memory hit` и сохранять отдельные
  episode-level lessons с выводом `helped/irrelevant/misleading/insufficient`;
- не давать reflection доступ к blind-only данным сверх зафиксированного attempt context и не давать
  blind-фазе `memory_store`;
- начать с file backend и тестового tool dispatcher, затем прогнать тот же контракт через Mem0;
- добавить метрики: число видимых признаков, retrieval calls, memory hits, episodes по эффекту,
  covered/skipped features, пустые и ошибочные retrieval, reflection lessons, stored lessons, latency
  и token cost.

Это именно граница исследования, а не окончательная спецификация. В частности, она не решает, как
должен выглядеть provider-native payload и нужно ли расширять `LessonInput` вместо упаковки feature
metadata в `content`.

## Открытые вопросы

- Должен ли workflow требовать ровно один retrieval-вызов для каждого видимого feature или разрешать
  модели пропускать признаки, которые она считает бесполезными?
- Какой feature state нужен для coverage: только `visible`/`not_visible` или также `uncertain` и
  `uninformative`? Как версионировать и менять реестр feature keys без поломки старых lessons?
- Должен ли grounded lesson с verdict `irrelevant` или `misleading` сохраняться так же, как
  `helped`, и какой формат лучше показывает его как counter-signal, а не как положительный факт?
- Должны ли `feature_key`, `memory_hit_id`, `source_attempt_id`, `effect` и idempotency key стать
  общими полями `memory_store`, или пока достаточно включать их в текст lesson?
- Tool должен возвращать нормализованные `Hint[]` или полный provider-native payload с общей
  оболочкой `memory_ref`/`feature_key`?
- Какой максимальный бюджет на одну фотографию допустим: число retrieval calls, время, токены и
  деньги? Как вести себя при частичном исчерпании бюджета?
- Для первой версии выбрать последовательный планировщик с фиксированным лимитом или batch tool
  calls: какое измерение latency/cost оправдывает более сложный вариант?
- Какие retry/backoff и timeout нужны для одного tool; что делать с malformed arguments, duplicate
  feature key, отменой run и `write_outcome_unknown`?
- Должен ли `memory_retrieve` видеть только observation text или также blind hypotheses/candidates?
  Передача гипотез увеличивает полезность поиска, но создаёт риск подтверждения первой догадки.
- Как будет измеряться качество episode-level lessons: общим geoscore, отдельным feature recall,
  ручной проверкой или комбинацией?
- Когда Hindsight и xmemory должны войти в runtime selection, чтобы tool contract проверялся не только
  на file/Mem0?
- Какой benchmark protocol фиксирует cold/warm режим, snapshot, порядок samples и отсутствие
  cross-run memory writes?
- Нужны ли quarantine/review и rollback для lessons, или для v1 достаточно immutable snapshots и
  ручного выбора snapshot перед evaluation?
