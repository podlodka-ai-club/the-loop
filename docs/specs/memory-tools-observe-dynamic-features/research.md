# Динамическое извлечение признаков фотографии

## Задача

Текущий flow требует от vision-модели вернуть фиксированные 12 слотов. Это даёт стабильную
структуру, но заставляет одинаково обрабатывать фотографии с разным содержанием и ограничивает
retrieval заранее выбранным vocabulary. Требуется, чтобы модель сама выбирала признаки, видимые в
конкретной фотографии, а память и reflection сохраняли эту границу.

## Ограничения

- Набор признаков и их количество должны зависеть от фотографии.
- Tools должны оставаться bounded: произвольный вывод модели не должен создавать бесконечные
  retrieval-вызовы, hits или prompt payload.
- Отсутствие признака означает, что retrieval для него не запускается; приложение не создаёт
  искусственные `not_visible` записи.
- Feature key и observation text приходят от модели, но проходят runtime validation и становятся
  application context для последующих вызовов.
- Evaluation, training isolation, provenance и episode-level reflection сохраняются.

## Варианты

Фиксированный registry сохраняет coverage, но не отражает разнообразие кадров. Полностью свободный
tool-loop даёт модели выбор, но не гарантирует bounded стоимость и coverage. Гибридный вариант —
bounded dynamic observe и управляемый последовательный retrieval по возвращённым признакам —
сохраняет свободу выбора признаков и контроль приложения.

## Вывод

Подход должен перейти к динамическому массиву model-generated features. Prompt содержит примеры
дорожных, текстовых, природных и архитектурных cues, но не enum. Application валидирует slug key,
уникальность, число элементов и длину текста; затем последовательно обрабатывает только этот
массив. Максимальное число признаков остаётся ограничителем бюджета, а не фиксированным набором.

## Граница решения

Динамические признаки меняют observation, retrieval, trace и fixture labels. Они не меняют формат
Guess, provider-native ranking внутри одной группы, geocoder, memory promotion или post-reveal
правило «один lesson на один feature + memory hit».
