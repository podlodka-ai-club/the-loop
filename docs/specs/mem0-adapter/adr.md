# Mem0-адаптер v1 без поддержки snapshot и restore

**Status:** Accepted
**Date:** 2026-08-28
**Authors:** Loci

---

## Context

Loci нужна отдельная реализация `Memory` поверх Mem0 Cloud с авторизацией по API key. Интерфейс
содержит четыре метода: `remember`, `recall`, `snapshot` и `restore`. Platform API напрямую
покрывает запись и ranked search, но не умеет замораживать и восстанавливать состояние.

Попытка представить snapshot новым пустым scope не сохраняет текущее состояние и потому не
является снимком. Export с последующей повторной записью facts меняет идентификаторы и embeddings,
а доступа к внутреннему store у Cloud-клиента нет. Эти компромиссы не нужны для первой проверки
записи и retrieval. Подробности API и рисков собраны в [исследовании](research.md).

Решение относится только к benchmark-интерфейсу `Memory`. Продуктовые контракты
[memory_store](/tools/memory_store.md) и [memory_retrieve](/tools/memory_retrieve.md) устроены иначе
и этим ADR не меняются.

## Options considered

**1. Поддержать точные снимки средствами Cloud** — желаемая гарантия, но Platform не предоставляет
backup/restore API, поэтому вариант недоступен в текущей публичной поверхности.

**2. Поддержать переносимые снимки через export и повторную запись facts** — использует публичный
API, но создаёт новые IDs и embeddings, поэтому восстановленное состояние не является точной копией.

**3. Эмулировать снимок отдельным scope** — дёшево переключает области памяти, но без копирования
или наследования новый scope пуст и не представляет состояние в момент вызова.

**4. Отложить snapshot и restore** — позволяет проверить нативные возможности Mem0 без ложных
гарантий; ограничивает применение адаптера сценариями, которым снимки пока не нужны.

## Decision

Первая версия Mem0-адаптера реализует `remember` и `recall`. Методы `snapshot` и `restore`
завершаются явной ошибкой «операция не поддерживается», не обращаются к Mem0 и не меняют состояние.
Поддержка снимков требует отдельного исследования и нового ADR.

`remember` использует нативное автоизвлечение Mem0 Cloud, а `recall` — Platform ranked search.
Правила построения запроса, scope, metadata, IDs и пустого ввода определяются в spec. Зависимость от
публичной модели данных Mem0 допустима; локальная canonical copy не создаётся.

Platform `add` асинхронен. `remember` считается успешным только после терминального статуса
`SUCCEEDED` и проверки видимости созданных facts. `PENDING` и `RUNNING` являются нетерминальными;
`FAILED`, неизвестный статус и неизвестный исход после timeout возвращаются как разные ошибки.
Нулевой результат extraction считается успешным no-op и учитывается в метриках качества.

Автоматический повтор после неизвестного исхода не выполняется без подтверждённой idempotency.
Orchestration прекращает такой запуск, карантинирует adapter instance и помечает pilot `agentId` как
одноразовый: поздно появившиеся facts не должны попасть в следующий pilot.

Ошибки адаптера различают как минимум неподдерживаемую операцию, неверный вход и недоступность
провайдера. Они не маскируются под успешный пустой recall. Точные категории и их отображение на
результат benchmark определяются в spec.

Orchestration до первого model call или memory write отклоняет запуск, которому нужны snapshots.
Поэтому v1 используется только в отдельном pilot/smoke-контуре записи и retrieval, а не как полная
замена памяти в существующем checkpoint/evaluation workflow.

## Rationale

Отложенная поддержка снимков — единственный вариант, который не выдаёт другую операцию за
`snapshot`. Он сохраняет границу Platform API и позволяет отдельно проверить извлечение
географических facts и их ranked retrieval.

Явная ошибка безопаснее приблизительного восстановления: вызывающий код сразу видит неподдерживаемую
возможность и не запускает evaluation с неверным состоянием. Аналогично, ошибка backend не должна
выглядеть как корректный пустой результат — иначе инфраструктурный сбой незаметно исказит метрики.

## Consequences

**Positive:**
- Первая версия не создаёт локальную копию Cloud-памяти и не обещает неподтверждённую
  воспроизводимость.
- Запись и retrieval можно проверять независимо от будущего устройства snapshot.
- Ошибки памяти остаются наблюдаемыми и не смешиваются с отсутствием релевантных facts.

**Negative:**
- Адаптер нельзя использовать в существующем контуре, который обязательно вызывает `snapshot`, без
  изменения orchestration или явного запрета такой конфигурации.
- Нельзя заморозить память для повторного evaluation, возобновить training с checkpoint или сделать
  rollback.
- Первый адаптер нельзя запустить как полную замену памяти в текущем snapshot-зависимом workflow;
  для него нужен отдельный pilot/smoke-контур.
- Качество автоизвлечения и его дополнительная стоимость остаются рисками первого пилота.
- `remember` получает дополнительную latency фоновой extraction и polling, а неизвестный исход
  нельзя безопасно повторить без гарантии idempotency.
- Текст lessons и metadata передаются внешнему сервису Mem0.
- Cloud остаётся единственной копией извлечённых facts: потеря проекта, retention или удаление
  данных необратимы. Для v1 это принимается только потому, что pilot data считается одноразовой.

**Neutral:**
- Scope, query, search policy, polling и visibility check определяются в spec; API key хранится
  только в `.env`.
- Адаптер зависит от публичных IDs, metadata и search response Mem0; обновление SDK требует
  повторного integration test.
- Решение о точных или переносимых snapshots откладывается до появления подтверждённой потребности.

## Success metrics

- `snapshot` и `restore` всегда возвращают различимую ошибку неподдерживаемой операции, не вызывают
  Mem0 и не изменяют сохранённые facts.
- Snapshot-зависимая конфигурация отклоняется до первого model call и до первой записи в память.
- Успешный `remember` соответствует `SUCCEEDED` и видимости созданных facts; неизвестный исход
  останавливает run, карантинирует instance, выводит pilot agent ID из использования и не запускает
  автоматический retry.
- На размеченных 30 lessons не менее 24 дают хотя бы один корректный географический fact; среди
  извлечённых facts в этой выборке нет сведений о пользователе или утверждений без опоры на lesson.
- На 30 frozen queries ожидаемый релевантный fact входит в первые пять результатов минимум в 24
  случаях; provider failure всегда отличается от корректного пустого результата.
